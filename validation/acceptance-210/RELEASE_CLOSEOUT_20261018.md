## 3. R1：保留 fork 需求，明确不能靠一句“正常上下文”获得的保证

现行产品／使用约定见 [运行域合同](../../docs/v2/FORK_RUNTIME.md)和
[已知限制](../../docs/KNOWN_ISSUES.md)。父方继续原实例、子方显式建立新域的功能不删除；
不以全业务线程退出、强制代理、自动 PID 文件名或仅字节输出替代需求。

| 场景 | 当前事实与本版审查建议 |
|---|---|
| 普通 libc fork、有效资源快照 | 保留父方持续运行、子方在返回后显式 process_init/create 的既有实现和回归；旧指针不可复活或普通销毁 |
| 本库 fd／映射／格式化区间 | 保留 DONTFORK、继承 fd 单次消费、资源／格式锁顺序；fork 等待库内临界区不等于停止全部业务线程 |
| `_Fork`、`vfork`、原始系统调用、信号／atfork 内重建、无可靠快照 | 按现行拒绝／不支持合同；不能把“程序返回了”当成重建得到授权 |
| 多进程争用同一个轮转目标 | 现行为单所有者、冲突 EBUSY，不是共同轮转。必须确认该合同是否满足需求；不满足则在 #218 列明确实现任务，不能默认算满足 |
| 任意宿主 libc／第三方回调／分配器状态 | 尚无通用保证；必须检查实际依赖和锁／回调关系，不以用户签字使已知不安全路径变安全 |

Linux man-pages 的 [fork(2)](https://man7.org/linux/man-pages/man2/fork.2.html)
明确：多线程 fork 的子方到 exec 前，通用安全调用范围限于异步信号安全函数。
**从 fork 返回到普通上下文，并不会自动解除这一限制。** 因此本项目完整重建只能作为
限定 Linux/glibc 实现、限定宿主组合的工程合同审查，不能宣传通用 POSIX 安全。

R1 审查记录须固定：libc 包版本／运行库摘要、宿主使用的时区／区域设置、stdio、
动态加载、printf 扩展和替换分配器；是否在 fork 周围并发使用、所需依赖如何恢复、
是否存在“父方持锁等待尚未产生的子方解堵”的环，以及每个必需组合的原始结果。
本库内部协调锁不保护任意第三方状态。未知组合不能凭一句“glibc >=2.31”自动获保证。
本轮没有取得新的部署宿主清单，不伪造该项已完成；已有库内与独立 FILE 锁测试保留，
不扩张为全部宿主库恢复证明。

## 4. R2：TSan 风险只接受明示结论

现有 31 项多线程 fork 后工作线程场景的原生覆盖缺口继续记为未覆盖，不能算执行通过。
已有 ASan/UBSan、真实父子运行、锁序／竞争负例、同步锚点和跳过清单审计分别保留。
[TSan 官方说明](https://clang.llvm.org/docs/ThreadSanitizer.html)指出它检测数据竞争；
ASan 的内存错误检查不能等价替代这项能力。

当前同树原始审计为 TSan **1040 注册／1009 执行成功／31 明确跳过**、
ASan/UBSan **1040 执行成功**、9 个同步 fork 成功标记和模型 **0／66／66**。
计数与源码／原件摘要可以重算；它们不是所有子进程指令仍受检测的证明。
`test_fork_runtime.c` 的同步后缀只将子方 `child_async` 改为 0，父方仍可能有
异步 worker 或持锁线程。GCC 13.3 上游
[`ForkChildAfter`](https://github.com/gcc-mirror/gcc/blob/releases/gcc-13.3.0/libsanitizer/tsan/tsan_rtl.cpp)
在父方多线程时启用报告／内存／同步忽略。当前 9 项审计没有证明 fork 前仅有一个线程，
因此只能称为“TSan 构建下的实际执行锚点”。此处据上游实现说明证明边界，
未认证 Ubuntu 运行库逐字等于该上游源码；31 项退出跳过也不是检测能力缺口的全部计数。
独立单线程 fork 模型的健康／真实锁序／真实竞争结果仍只适用于模型自身。

建议对已登记的 31 项逐项核对最终候选的跳过理由、同源可执行替代和审阅结论，
不全局关闭检测器，不把退出 77、超时、信号或意外诊断改记为成功。
若接受有限组合证据，C_TSAN 必须是准确的风险接受，不能写“31 项已被 TSan 证明”；
若要求全部原生检查，则 #221 继续是阻塞，不能合并实验 #227 充数。
[既有有限模型](../../docs/v2/TSAN_FORK_MODEL.md)与定制运行库实验相互独立。

## 6. R4：性能验收方案，不把测得上界当成理论值

### 6.1 既有能力和真实缺口

复用 [现有基准](../../BENCHMARK.md)与
[固定到达率流程](../../.github/workflows/release-candidate-fixed-rate.yml)，不新建基准系统。

`null` 是文件后端 `/dev/null`，不是跳过 Logger 的零开销基线。

当前 #265 的 schema 2 已逐槽保存 API 耗时、到达迟到和返回状态，按 0、
`-EAGAIN` 与其他错误分类；`api_success_ns` 由真实返回 0 的样本计算，不能再列为
未实现。`api_ns` 仍包含所有尝试调用；成功调用表示异步接收，不表示逐条落盘。
文件后端核对预热／测量每个 phase/seq 的出现集合与次数，#266 的预算超限和归档
失败原件保留也已进入主线。`flush_ns` 是每阶段一次排空后的批量屏障，
不是逐记录持久化分位；CPU/RSS 包含驱动及初始化／预热开销。
若需要逐记录持久化 P99 或纯库 CPU 成本，仍需对应测量；同步、Syslog及轮转负载
不由此异步矩阵代表。不同历史提交的 schema 1 结果保留原口径。

固定到达率工作流的 PR／main push 自动触发受其列明路径过滤，也支持手动
`workflow_dispatch`；主线其他工作流全部成功不能推出最新生产源码已经执行该专项。
#266 的历史 32＋32 样本只属于其原始受测提交，
不得替代 #272 之后的准确候选数据。

本轮补测上述准确 main 时，静态第 8 个样本已完成测量和归档，但临时目录清理返回
`ENOTEMPTY`，未处理异常使 runner 退出 1、汇总仅有 7 行；剩余静态和共享负载未运行。

建议初始可复现矩阵（尚非已批准业务负载）：静态／共享分别执行，1/4生产者，
总计划速率10k/50k，正文64/1024字节，null/file，预热1秒、测量5秒、5轮交错。
每种链接形态80样本；每样本最多300000计划调用，按现有上限估算
`300000*(1024+512)=460800000`字节，小于1GiB。样本45秒超时、200样本与总证据
1GiB限制保留；达到预算时保留失败记录，不删失败样本继续凑齐成功次数。
这是短窗口基线，不是持续稳定性或饱和极限认证。10k/50k不是对外吞吐承诺。

在实际待测文件系统内指定一个专用临时目录，以既有脚本运行：

```sh
# 先按 BENCHMARK.md 用 Xmake 构建生产库和 bench_fixed_rate，核验实际优化和链接。
# BIN/LIB/BUILD_LOG 为该次真实构建产物；OUT 必须是全新目录；TMP_ROOT 不指向业务日志。
python3 scripts/benchmark_fixed_rate.py \
  --binary "$BIN" --library "$LIB" --build-log "$BUILD_LOG" --out "$OUT" \
  --threads 1 4 --rates 10000 50000 --payload-bytes 64 1024 --backends null file \
  --seconds 5 --warmup 1 --repeats 5 --timeout 45 --temp-root "$TMP_ROOT"
```

先固定阈值再运行，不能看到结果后移动标准。建议的初始审查阈值为：非过载验收点
计数／文件完整性全通过、Logger丢弃0、I/O失败0；发生器缺失超过0.1%或到达迟到
P99超过1ms时先判负载未被充分实现。相对同机同配置参考，5轮中位有效输出吞吐
下降超过5%或API P99上升超过10%时阻断调查。**这些数值仅是待批准的筛查建议，
不是用户给定SLO、理论达标线或现有CI已经执行的阈值。** 噪声／环境不一致时记未判定，
不直接认定库回归，也不自动放行。绝对QPS/P99与CPU/RSS预算仍须明确后才能验收。

输出吞吐用 `emitted / output_observed_seconds`，不使用计划速率替代；同时报告
实际attempted、generator_missed、丢弃／回退及原始迟到分位。逐轮报告和全部失败
样本保留，不把各轮P99取平均称为合并P99。需要合并分位时从同类原始样本重算。

### 6.3 “理论指标”的可核查解释

先建立并校准明确假设的资源需求模型。示例：P个有效生产者、每条生产侧必要服务
时间tp、共享串行资源的每条总需求ts、实际输出长度L、指定持久性模式的带宽BW：
`Q <= min(P/tp, 1/ts, BW/L)`。若同步确认严格按每批B条串行等待持久化，再加入
`B/tflush`约束；现有异步每阶段flush测试不能直接套此项宣称逐条持久吞吐。

同一格式锁在生产／消费两侧的需求必须合计，不能把两个相关瓶颈当成独立资源；
L包含元数据而非只用payload。tp/ts/BW必须来自匹配资源与工作负载的独立校准和
模型假设，不从待验库的整库吞吐倒推出同一“理论上限”制造100%达标。
模型上界、实测容量下界、业务SLO和相对回归是四件不同的事；当前没有已校准参数，
不填通用百万QPS、固定效率百分比或未经测量的缓存行硬件计数。

## 7. R5：冻结与签收的顺序必须匹配现有门禁

[现有检查器](../../scripts/check_release_signoff.py)要求冻结基线B必须是签收提交S的
祖先，且B到S唯一变化是 `validation/release_signoff_v2.json`。
所以顺序固定为：**本文等文档／获批修复／性能方案完成 → 基线B → 基线证据与真实
决策评论 → 仅签收JSON的提交S → 检查S和制品 → 独立标签授权 → 正式发布与远端复验**。
冻结后再改文档、工作流、测试或源码必须选新B并重核受影响证据，不能删除该保护。

每项决策必须在原映射的 #100/#218/#221/#210/#106/#107/#212 对应评论留存：
精确范围、接受人、UTC时间、证据、残余风险及后续对象；12个字段引用这些真实评论。
检查器验证的是一致性，不认证评论作者；维护者核对与受保护分支／标签仍不可省。
本轮未认证远端保护设置，不把本文描述视为保护已配置。F_RELEASE 是发布前授权，
其证据是候选包／来源，不要求先有正式Release才能签署；发布后另验实际资产，避免循环。

正式产物为静态TGZ＋其SHA256、共享TGZ＋其SHA256四件；从获批固定源码构建，
检查基线及重定位消费、ABI／43符号／生产隔离／文档，再从远端重新下载核对摘要、
标签指向、标题和稳定类别。历史等价证据保留原SHA并写“未重新执行”，正式包不能
冒用历史包。本轮不创建标签，不调用release-publish，不修改12项pending。
