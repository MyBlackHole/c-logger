# 锁依赖调试检查

状态：#103 跟踪基础设施与 #126 获取前检查已实现。

c-logger 使用显式线程本地（TLS）持锁栈检查项目锁契约。调试/测试构建启用
lockdep；生产构建通过 `LOGGER_ENABLE_LOCKDEP=0` 将检查与记账编译为空操作。

当前实现跟踪以下八种锁类；Audit 锁及专属回归已退役。运行域锁随 #218 接入同一跟踪器，不另建平行锁模型。

## 跟踪的锁类别

- Global 控制锁
- Global 生命周期锁
- 实例输出锁
- 实例进度锁
- 队列等待锁
- Console 输出锁
- 进程运行域格式协调锁
- 进程运行域资源协调锁

允许的嵌套关系来自 `docs/v2/LOCKING.md`：

```text
Global 控制锁 -> Global 生命周期锁 -> 一把实例锁
Global 控制锁 ---------------------> 一把实例锁
```

第二条只用于控制器独占的候选对象或已完成撤销发布/排空的对象。
实例锁之间禁止嵌套。Console 不得进入 Global 或实例锁层级，但可进入格式协调。

运行域附加边固定为：

```text
Global 控制/生命周期锁或实例输出锁 -> 格式协调锁 -> 资源协调锁
Global 控制/生命周期锁或实例输出锁 -------------> 资源协调锁
Console 输出锁 -> 格式协调锁
```

资源协调锁为最内层；禁止资源到格式、Global、实例或 Console 的反向获取。
进度锁与队列等待锁不允许持有时再获取这两类运行域锁。资源函数内部已拥有租约时
只能调用标明已持锁的内部操作，不重复获取同一地址。

## 检查与记账时机

跟踪只覆盖项目显式接入的互斥锁/读写锁路径，不拦截任意 pthread 调用：

- 可能阻塞的互斥锁、读写锁的读锁和写锁：先无副作用地检查参数、递归
  获取、锁顺序及 TLS 栈容量，再调用 pthread 原语；只有原语成功后才
  登记到 TLS。
- 互斥锁尝试加锁和读写锁尝试写锁：先执行非阻塞 pthread 原语。失败时
  原样返回 pthread 错误码，不检查锁顺序，也不改变 TLS；成功后再检查并登记。
- 解锁：先检查当前线程 TLS 栈顶的锁类别、对象地址及 LIFO 顺序，再调用 pthread
  原语。pthread 解锁成功后才移除记账；失败时按既有路径放弃跟踪该项并把错误
  交由调用方处理。对象封闭方式仍由相应同步错误契约决定。
- `pthread_cond_wait()` 的互斥锁在等待期间由 pthread 暂时释放，并在返回前重新获取。
  这次等待不改 TLS 持锁栈；返回后仍按已持有处理，最终通过跟踪解锁释放。

## 已接入调用点

- Global 的 `g_control_mu` 与 `g_lifetime_lock`：分别使用互斥锁包装和共享
  `LOGGER_LOCK_GLOBAL_LIFETIME` 类的读写锁包装。
- 实例输出锁、实例进度锁、队列等待锁和 Console 互斥锁：通过显式锁类别 guard 接入；
  `logger_sync_outputs_locked()` 在调用点断言输出锁已持有。

- `logger_libc` 的格式协调及 `logger_fork_fd` 的资源协调均通过带类别的
  `__cleanup_lockdep_mutex_*` 接口接入。实际 pthread 调用仍存在于生产构建，
  只有跟踪记账在 LOCKDEP=0 时去除。
- 成功 fork 的子处理函数只清当前线程的持锁栈深度，不解锁已被 DONTFORK
  隔离的旧地址。父方持锁栈依旧按资源、格式的逆序释放。

这些检查分别由 `logger_lockdep_check_acquire()` 和
`logger_lockdep_check_release()` 提供。检查函数本身不改变 TLS 状态；成功获取/释放
后的跟踪器 API 才更新持锁栈。关系矩阵、Global 锁图和条件变量约束见
`docs/v2/LOCKING.md`。

## 诊断与边界

调试/测试还提供：

- `logger_lockdep_assert_held()`
- `logger_lockdep_assert_not_held()`

发生递归获取、禁止锁序、错误释放顺序或断言失败时，调试/测试构建输出锁依赖诊断
并 `abort()`。生产构建不启用这些诊断，也不改变原有错误模型。

这不是完整 Linux lockdep 的用户态移植：实现使用固定锁类别关系表和固定容量 TLS
持锁栈，不推导动态锁图，不观测项目未接入包装的 pthread 锁，也不分析任意程序的
锁依赖。检查只证明已建模锁类别及已接入调用点满足本项目契约。

回归场景覆盖真实 NORMAL 互斥锁自重入、两线程反向锁序、错误解锁前置诊断、失败
trylock、读写锁转换、TLS 线程隔离及条件变量等待返回后的记账状态。完整构建与测试
命令由仓库测试配置和 CI 维护。

## 运行域正反验证

`xmake test -g libc-coordination -j1` 的 `order-ok` 实际取得格式锁再取得资源锁；
`order-reversed` 和 `order-recursive` 在独立子进程内必须以 SIGABRT 结束，
并设置超时防止“先死锁后被杀”伪装成锁序检查。该目标使用 LOCKDEP=1 支持库，
不是生产库内启用诊断。其余场景按准确 mutex 地址注入失败，验证解锁错误不丢失、
主操作错误优先、GNU `%m` 保留调用方 errno，以及同步/批量格式失败不记成功。
