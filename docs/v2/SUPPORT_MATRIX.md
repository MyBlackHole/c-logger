# c-logger 2.0 支持基线

本文件冻结 2.0 初始工程基线。扩大支持范围必须有独立设计、CI 和运行证据，不能仅因为“理论上能编译”就宣称支持。

<a id="初始-production-目标"></a>

## 初始生产目标

| 项目 | 2.0 初始基线 |
|---|---|
| 操作系统 | 仅 Linux |
| CPU | x86_64 |
| ELF | ELF64 |
| 最低 Linux 内核 | 5.10 |
| 最低 glibc | 2.31 |
| C 方言 | GNU C11 |
| GCC | >= 9 |
| Clang | >= 10 |
| Xmake | >= 2.8.5；CI 固定 3.1.1 |
| 链接形式 | 共享库 + 静态库 |
| C++ 消费方 | 公开头文件对 C++11 消费方保持可用 |
| musl | 不在初始支持范围 |
| AArch64 | 不在初始支持范围 |
| 32 位 | 不支持 |

## 证据要求

当前 v1 已有：

- Ubuntu 20.04/glibc 2.31 运行时门禁；
- Linux 5.10 虚拟机门禁；
- x86_64 ELF/SONAME/GLIBC 版本上限检查；
- 共享/静态安装消费方验证。

2.0 必须保留等价或更强证据。

GCC 9 是 Ubuntu 20.04 的工程基线；Clang 10 是 2.0 的最低目标版本。`.github/workflows/v2-engineering-baseline.yml` 在 Ubuntu 20.04 用户态分别使用 GCC 与 Clang 构建并运行完整静态测试集，同时记录实际编译器版本。该门禁成功后，GCC/Clang 基线才视为已有可重复 CI 证据。

## 扩展规则

新增 AArch64、musl 或更旧用户态不是普通修复，必须同时回答：

- C11 原子/内存序语义是否仍成立；
- ABI/布局是否变化；
- 系统调用/libc 行为差异；
- 运行时检测器（sanitizer）/工具链是否可用；
- 打包与安装消费方是否验证；
- 崩溃/持久性门禁是否需要新平台运行。

支持矩阵变化必须在 2.0 ABI 冻结前完成，或作为后续明确版本能力发布。


## 编译期守卫

2.0 初始编译门禁：

- 新增 VLA 通过 `-Wvla` 暴露，并在正常 `-Werror` 目标中成为错误；
- 生产库及其同源测试/回归支持归档对超过 24 KiB 的单函数栈帧发出诊断；历史测试可执行文件不在这一轮被强制重写；这是用户态初始防护线，不等于 Linux 内核栈大小；
- 24 KiB 是当前编译门禁阈值，不是当前源码的实测最大栈帧。最初设值参考的 Audit 函数已退役；后续收紧必须基于普通 Logger 的新栈使用清单，扩大阈值仍须审查依据。
