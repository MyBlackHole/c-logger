# 队列构造的记录数与字节数

本阶段实施 #106/#210 的 D1/T2 在队列构造计算链上的有限子集。
主槽位数、溢出块数与存储字节数原来都使用 `size_t`，计算接口不能拒绝
把字节数传成记录数，或把字节输出写入记录数槽。本轮提供不同结构体的
编译约束；源码审查没有复现既有容量取整或乘加检查的生产算术错误。

## 范围与类型边界

私有头 `src/logger_queue_size.h` 定义两种结构类型，底层均为 `size_t`：

| 类型 | 本轮对象 |
|---|---|
| `logger_queue_records` | 请求容量、取整后的主槽位数、溢出块数 |
| `logger_queue_bytes` | 构造计算中的溢出存储字节数、合计存储字节数 |

真实生产实现中的三个 `static` 接口按单位传递参数和输出：

- `queue_capacity` 接受记录数，并只向记录数槽写出成功的取整结果。
- `queue_spill_capacity` 接受和返回记录数。
- `queue_storage_size` 接受两种存储的记录数，只向字节数槽写出合计。

`logger_queue_init` 在进入计算链时显式构造请求记录数；局部结果保持类型，
到现有 `struct logger_queue` 字段和 `logger_runtime_calloc` 接口时显式提取 `.value`。
新头不安装，三个计算接口仍为文件私有，不新增公开符号。

主槽位与溢出块在本层使用同一种计数类型，二者对调不由类型本身拒绝。
同型复制、强转、显式取 `.value` 后重建仍是 C 的逃逸方式。公开 `size_t`
入口、现有队列字段、诊断和分配器接口不因此获得全程序单位数据流保证。
本轮不宣称完成 D1/T3 的索引／计数或 D1/T4 的代次／序列隔离。

## 保留的算术、布局与错误合同

私有 `logger_queue_init` 的请求 0、1、2 都取整为 2；其他请求向上取整到
2 的幂。公开配置的 `queue_capacity=0` 仍表示原有默认值 8192，二者不能混同。
取整后的容量必须小于位置空间的一半，并通过主槽位乘法检查。
溢出池继续取主容量与 `LOGGER_QUEUE_SPILL_LIMIT`（1024）的较小值。

合计存储大小先检查溢出池乘法，再检查主槽位与溢出存储的乘加；失败不写出
字节结果。`queue_storage_size` 返回负错误码，私有构造接口继续返回
`-1` 并设置 `errno`。这些是既有数值与错误语义。

`struct logger_queue`、槽位和消息的布局不变。入队／出队位置、槽位序列、位图、
原子内存序、唤醒和完成水位协议均沿用既有实现。记录成功入队后的语义见
[队列存储](../QUEUE_STORAGE.md)和[唤醒协议](QUEUE_WAKEUP_PROOF.md)。

构造仍按原次序计算并保存 `cap`、`mask`、`spill_cap`、`storage_bytes`，再
取得主槽位和溢出存储；只有两个分配和同步对象初始化均成功后才发布
`q->slots`、`q->spills`。第二个分配失败时，第一块由原有作用域清理真实归还，
同时保留主要 `errno`。失败时已有几何字段不等于存储所有权已经发布。

合计数只包括两块有效负载。`logger_runtime_calloc` 仍另行检查自己的私有
分配头和真实映射错误；通过队列的算术检查不承诺操作系统能够分配该容量。
两处获取实参同步登记在 `validation/runtime_alloc_sites.tsv`，获取位置总数不增加。

## 运行验证

`xmake test -g queue-size -j1` 需要 `build_regression_tests=y`。
`tests/regression/test_queue_size.c` 用链接期包装观察真实
`logger_runtime_calloc` 的记录数和元素字节数，并转发实际分配与释放。
故障只存在于测试可执行文件；生产库不增加故障分支。

| 场景 | 验收对象 |
|---|---|
| `minimum` | 私有请求 0／1／2 的最小容量、两次真实分配与释放 |
| `round-up` | 非 2 次幂请求向上取整，实际分配参数与存储字节一致 |
| `spill-limit` | 1023／1024 请求对应的池容量边界 |
| `spill-capped` | 主容量超过 1024 后，溢出池仍封顶为 1024 |
| `max-capacity` | 最大算术可接受容量到达首个分配入口，参数不溢出；入口主动返回 `ENOMEM`，不执行巨额映射 |
| `capacity-overflow` | 超过可接受容量、半位置域和 `SIZE_MAX` 请求在取得存储前拒绝 |
| `first-allocation-failure` | 第一次分配失败，未发布存储、没有虚假释放，错误码保留 |
| `second-allocation-failure` | 第二次分配失败，第一次成功的存储恰好实际释放一次，错误码保留 |

正常小容量场景真实执行短、长消息的入队／出队并核对内容、溢出池归还和
最终释放。失败场景检查未发布的指针、等待错误状态和运行域分配计数，随后在
同一进程恢复健康构造与使用。最大容量场景只证明参数和错误处理，不算真实
大容量分配成功，也不把任意静态辅助函数输入都称为公开配置可达路径。

静态配置对回归支持归档与真实生产归档分别运行 8 个场景，再加编译契约，
共 17 个注册项。共享配置保留支持归档 8 项和编译契约，共 9 项；
GNU `--wrap` 不拦截 DSO 内部，真实共享库另由既有公开／安装测试验证。
原有 MPSC 并发、位置回绕、六种子 FIFO 模型、构造回滚和工作线程测试继续执行。

## 编译验证与保证边界

`tests/scripts/test_queue_size_types.py` 使用 Xmake 实际回归目标的编译器，
包含真实 `logger_queue.c` 或在该文件上做唯一位置变异，验证参数、输出槽和
生产调用的单位误混。每套编译器执行 12 对正反例和 1 个显式逃逸正例，
共 25 次语法编译。每个反例先执行仅修正类型的正例；负例必须在准确变异行
得到不兼容类型诊断，缺少工具／头文件、语法错误、信号与超时不能算通过。
另有显式 `.value` 逃逸正例，记录本轮防护的边界。

编译约束和列出的运行回归分别验收，不把其中之一当成所有 C 路径的证明。
这项有限实现不修改发布签收，不代表 D1 全部完成或 2.0 正式发布。
