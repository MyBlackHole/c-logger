# c-logger 2.0 所有权与生命周期设计

状态：**#102 设计基线，已按当前不含 Audit 的 ABI 2 对象图更新**。

当前设计入口见 [README.md](README.md)。Audit/密码学模块已退役，不属于本文的对象或验证范围；迁移边界见 [AUDIT_REMOVAL.md](AUDIT_REMOVAL.md)。

本文记录当前实现的所有权语言、对象图和选择生命周期原语的条件。当前保留 Global 外观接口，
显式实例采用由宿主拥有对象、使用者借用、宿主停止并等待借用者退出的模型；公开 API/ABI 最终冻结仍需 #104/#108 审查，
未来提案不改变这里记录的现行调用与销毁合同。

核心原则：

> 先证明谁拥有对象、谁只是借用、谁负责停止执行者，再选择引用计数、锁或其他原语。

## 1. 所有权分类

统一使用以下分类：

```text
AUTO
OWNED
BORROWED
MOVED
SHARED
REFCOUNTED
```

<a id="auto"></a>

### 自动作用域资源（AUTO）

词法作用域内唯一所有者。适合临时 fd、堆候选资源、临时 FILE、尚未发布的替代资源，可以使用 `__free` / 清理辅助函数。

<a id="owned"></a>

### 独占拥有（OWNED）

结构性唯一所有者。所有者决定资源最终释放时间。

例如：

- `logger_t` 结构性拥有队列/后端/工作区；
- 队列结构性拥有槽位/溢出块池。

<a id="borrowed"></a>

### 借用（BORROWED）

只能在明确的生命周期证明覆盖期间访问。

BORROWED 不延长对象生命周期，不能执行最终释放，不能逃逸其生命周期作用域，也不能因为“有一把锁”就假设自己拥有对象。

<a id="moved"></a>

### 已转移（MOVED）

所有权已从源转移到目标。移动后源必须进入无资源状态，禁止重复释放。

<a id="shared"></a>

### 共享访问（SHARED）

描述多个执行者可以访问同一对象，但**不自动意味着引用计数**。

共享访问必须单独说明结构所有者、读者生命周期证明，以及销毁如何等待共享访问结束。

<a id="refcounted"></a>

### 引用计数管理（REFCOUNTED）

只有多个**独立所有者**都可以延长对象内存生命周期时才使用。

引用计数只证明“对象内存当前仍有所有者”，它不证明对象仍处于 RUNNING、后端可用、工作线程已停止、关闭已完成，或当前线程允许执行可阻塞的销毁流程。

## 2. 不可替代关系

始终成立：

```text
lock != lifetime pin != join != refcount != atomic

refcount != admission state
refcount != execution quiescence
close != final free
queue empty != backend completion
atomic != ownership
```

## 3. 当前 2.0 基线判断：logger_t 不预先改成 REFCOUNTED

当前代码中的实际关系是：

```text
宿主 / Global 控制器
        |
        | OWNED
        v
     logger_t
        |
        +---- OWNED ---- 文件后端
        |
        +---- OWNED ---- syslog 后端
        |
        +---- OWNED ---- 队列
        |                   |
        |                   +---- OWNED ---- 槽位
        |                   |
        |                   +---- OWNED ---- 溢出块池
        |
        +---- OWNED ---- 工作线程工作区
        |
        +---- OWNED ---- pthread 工作线程生命周期
                             |
                             +---- BORROWED ---- logger_t
```

工作线程是 Logger 的**从属执行者**，不是独立所有者。

因此 #102 的基线决定是：

> **不因为 2.0 引入引用计数原语就让 logger_t 自动采用引用计数管理。**

如果 #104 后续证明 SDK、插件或其他对象确实具有“可以独立于宿主延长 Logger 生命周期”的需求，再重新打开该决定。

<a id="为什么不做-per-log-refcount"></a>

### 为什么不做逐条日志引用计数

禁止把：

```text
logger_log()
    get
    ...
    put
```

作为默认安全方案。

原因：

- 每条日志增加原子 RMW；
- 仍不能解决“裸指针指向的内存已经被并发释放后才执行 get”的问题；
- 混淆调用方所有权与 API 调用同步；
- 关闭/最终 put 执行上下文更难证明。

如果未来采用引用计数，应优先是**长生命周期引用**：

```text
创建 SDK 实例 -> get
SDK 生命周期  -> borrow
销毁 SDK 实例 -> put
```

而不是每次日志调用 get/put。

<a id="4-refcount-的严格引入条件"></a>

## 4. 引用计数的严格引入条件

只有同时满足以下条件才允许一个对象变成 REFCOUNTED：

1. 存在两个或更多独立所有者；
2. 任一所有者都可能比创建者活得更久；
3. 所有者之间不能通过更简单的结构化 join/父对象生命周期管理；
4. 最终释放的执行上下文可以明确证明安全；
5. 引用计数成本和泄漏风险小于替代方案复杂度。

如果这些条件不成立，优先：

```text
单一结构所有者 + BORROWED 使用者 + 显式静止状态
```

<a id="refcount-本身的安全规则"></a>

### 引用计数本身的安全规则

未来若实现 `logger_refcount_t`，必须满足：

- 0 是终止状态；
- 禁止从 0 到 1 的复活；
- 上溢不得回绕；
- 下溢不得回绕；
- 最终释放只能发生一次；
- 上溢/下溢/不变量失效不得导致错误的内存释放；
- 证明失败时保留/泄漏优先于 UAF。

特别注意：

> `inc_not_zero(ptr->ref)` 只有在调用者已经有办法证明 `ptr` 本身仍可安全解引用时才合法。

它不能让一个可能已经被其他线程 `free(ptr)` 的裸指针重新变安全。

## 5. Logger 的 BORROWED 调用模型

当前基线：

```text
所有者创建对象
    ↓
向从属使用者发布指针
    ↓
所有者保证生命周期期间，使用者进行 BORROW 访问
    ↓
所有者关闭这些使用者的准入
    ↓
所有者停止并 join 外部借用者
    ↓
Logger 销毁
```

因此：

- Logger 内部不能假装知道宿主所有外部线程；
- 公开销毁接口不能“扫描线程”证明无调用方；
- SDK/插件若只是 BORROWED，宿主必须先停止并 join 它们；
- 如果未来 SDK 成为真正独立所有者，应显式升级为 get/put 契约，而不是继续写“借用”。

#104 可以改变公开对象模型，但必须显式更新这里的所有权图。

<a id="6-worker--queue--workspace"></a>

## 6. 工作线程 / 队列 / 工作区

<a id="worker"></a>

### 工作线程

工作线程持有：

```text
BORROWED logger_t *
BORROWED logger_queue_t *
BORROWED worker_workspace *
```

证明：

```text
Logger 最终销毁
    ↓
running = 0
    ↓
唤醒工作线程
    ↓
pthread_join 成功
    ↓
工作线程借用结束
    ↓
可以销毁工作区/队列
```

禁止工作线程对父 Logger 加引用计数来替代 join，也禁止 join 失败后继续释放工作线程可访问内存。

<a id="queue"></a>

### 队列

`logger_t` 结构性拥有 `logger_queue_t`。队列结构性拥有槽位、溢出块池、等待互斥锁/条件变量。

销毁：

```text
没有生产者/消费者
    ↓
工作线程已 join
    ↓
销毁等待同步对象
    ↓
释放溢出块/槽位
```

同步对象销毁失败属于生命周期证明失败，不得继续释放队列存储。

<a id="record-ownership"></a>

### 记录所有权

异步入队后必须完成与源数据生命周期的隔离：

```text
调用方数据
   |
   | 复制/捕获
   v
队列拥有的槽位 / 溢出块
   |
   | 消费者复制
   v
工作线程拥有的批次工作区
   |                         消费者复制完成后（仍在 try_pop 内）
   |                             -> 归还溢出块
   |                             -> slot.seq release，槽位可复用
   |                             -> 推进 dequeue_pos
   |
   | 后端输出尝试（成功或失败）
   v
async_completed / 完成水位
```

`logger_queue_try_pop()` 在复制完整记录后即归还溢出块/槽位；工作线程随后只访问自己的批次副本。
因此队列存储复用与后端完成是两个不同事件。`logger_worker_main()` 在
`emit_batch()` 返回后推进完成计数，并在同步协议正常时于 `progress_mu` 下推进 `completed_pos`。
后端 I/O 失败也会完成该次尝试并记录错误；完成不承诺成功或通过 fsync 实现持久化。
flush 等待预留水位，不能用队列为空、出队或槽位/溢出块可复用替代。

队列中不能保存调用方的可变裸指针。

<a id="7-backend-ownership"></a>

## 7. 后端所有权

<a id="file"></a>

### 文件后端

`logger_file_t` 是所有权可转移的单一所有者资源。

```text
AUTO fd 候选资源
    ↓ 验证
MOVED 至 logger_file_t
```

重新打开/轮转：

```text
准备候选资源
    ↓
验证候选资源
    ↓
同步/提交先决条件
    ↓
安装新所有者
    ↓
退役旧 fd
```

简单重新打开操作中，候选资源准备失败时保留仍可用的旧所有者。轮转成功重命名后，旧 fd 已属于归档；
后续活动文件创建/同步失败进入已分离状态，不能继续写旧归档。两条路径不能合并为“轮转失败永不改变旧状态”。

<a id="syslog"></a>

### Syslog 后端

`logger_syslog_t` 由 Logger 唯一拥有。套接字替换/重连候选资源失败时丢弃候选资源，不能把失败套接字伪装成有效所有者。

后端不独立延长 `logger_t` 生命周期。

<a id="8-global-ownership"></a>

## 8. Global 所有权

当前实现：

```text
Global 控制器
    |
    | OWNED
    v
  g_logger
    ^
    |
BORROWED 读者
    |
g_lifetime_lock 读侧生命周期固定保护（pin）
```

`g_lifetime_lock` 是生命周期固定保护（pin），不是引用计数。

关闭：

```text
关闭准入
    ↓
获取生命周期写锁
    ↓
等待旧读者排空
    ↓
g_logger = NULL
    ↓
释放生命周期锁
    ↓
保持控制器独占期间销毁旧 Logger
```

当前 Global 外观接口使用上述协议。#104 若将来提出替换或删除，必须作为新对象模型决策重新审查，不能把未来选项当作现行行为。

禁止仅因为已有引用计数就替换成裸原子指针 + `inc_not_zero`；这存在“先释放内存、后访问引用计数字段”的根本竞态。

<a id="9-process-census-不是-refcount"></a>

## 9. 进程存活对象计数不是引用计数

`live_objects` 的语义是进程/fork 生命周期中的存活对象计数，不是 `logger_t` 引用计数。

因此：

- 计数降至 0 不触发 Logger 释放；
- 获取存活对象计数不产生 Logger 所有者；
- 释放存活对象计数不代表对象最终 put；
- 上溢/下溢是进程生命周期不变量失效。

禁止把存活对象计数与对象引用计数合并。

---

<a id="10-构造失败-rollback-必须使用同一套-lifetime-proof"></a>

## 10. 构造失败回滚必须使用同一套生命周期证明

当前构造回滚已遵守以下边界：

> **构造回滚与正常销毁具有同样严格的“先证明安全，再释放内存”要求。**

不能因为对象“尚未发布”就认为所有同步对象的销毁必然成功，然后无条件 `free(container)`。

构造过程必须记录已经成功建立的资源，例如：

```text
ALLOCATED
EMIT_MUTEX_READY
PROGRESS_MUTEX_READY
PROGRESS_COND_READY
FILE_READY
SYSLOG_READY
QUEUE_READY
WORKSPACE_READY
WORKER_STARTED
PUBLISHED
```

回滚只释放确定已经建立的资源，并按依赖顺序先停止/join 执行者，再释放其可达资源；不要求互相独立的资源机械地按文本逆序释放。

如果以下证明失败：

- 工作线程 join；
- 队列同步对象销毁；
- 进度/输出同步对象销毁；
- 进程存活对象计数释放；

则：

```text
不释放容器
不释放尚无法确认已退出的使用者仍可访问的内存
记录不变量/生命周期失败
原构造失败仍为首要错误时，返回该错误
```

清理失败的优先级必须单独定义，不能覆盖首要构造错误后让调用方误判根因。

未发布的对象没有合法外部借用者，但同步对象销毁失败仍代表内部不变量无法证明。

2.0 继续坚持：

> 证明失败 -> 安全保留/泄漏，不能为了“构造失败必须无泄漏”冒 UAF 风险。

<a id="11-cancellation-ownership-handoff"></a>

## 11. 取消时的所有权交接

成功构造但尚未把所有权返回调用方时，库仍是 OWNED。只有函数真正返回指针后所有权才转移给调用方。

待处理的取消请求必须在所有权交接前解决。

恢复取消前：

- 库锁已释放；
- 生命周期固定保护（pin）已释放；
- 词法作用域资源已清理。

取消不等价于事务回滚。

---

## 12. fork / dlclose

fork 子进程不获得一个“可继续使用”的 Logger 所有者。继承的 pthread 状态、fd 和对象内存保持不可安全复用状态，直到 exec/_exit。当前没有 fork 后重新初始化或继承运行时的原地重建接口。

不能通过重置互斥锁、重置引用计数或修改所有者 PID 伪造安全的新生命周期。

任何可能执行 Logger 代码的借用者/工作线程/回调必须在 dlclose 前退出。引用计数只能保护堆对象，不能保护已经被卸载的 DSO 代码段。

## 13. 2.0 所有权矩阵

| 资源 | 创建者 | 结构所有者 | 借用者 | 移动点 | 静止状态证明 | 最终释放 |
|---|---|---|---|---|---|---|
| logger_t | 创建函数/控制器 | 宿主或 Global 控制器 | 公开调用方/工作线程 | API 交接 | 调用方协议 + 工作线程 join | Logger 销毁 |
| 工作线程 | logger_t | logger_t | 无独立所有者 | 无 | pthread_join | Logger 销毁 |
| 工作区 | logger_t | logger_t | 工作线程 | 无 | 工作线程已 join | 工作区销毁 |
| 队列 | logger_t | logger_t | 生产者/工作线程 | 无 | 生产者静止 + 工作线程已 join | 队列销毁 |
| 队列槽位/溢出块 | 队列 | 队列 | 生产者/消费者临时访问 | 入队/消费协议 | 槽位代次协议 | 队列销毁 |
| 文件后端 | 构造函数 | logger_t | 输出路径 | 候选资源安装 | 输出路径已静止 | 文件关闭 |
| syslog 后端 | 构造函数 | logger_t | 输出路径 | 候选资源安装 | 输出路径已静止 | 套接字关闭 |
| 全局 Logger | logger_init | Global 控制器 | 全局调用 | 候选资源发布 | 生命周期读者已排空 | 全局关闭 |
| 进程存活对象计数 | 进程层 | 进程层 | fork 门禁 | 无 | 经检查的递减 | 非对象释放机制 |

#102 后续实现或 #104 对象模型改变时必须同步维护该表。

## 14. 第一阶段设计决定

当前冻结：

1. `logger_t` **不预先变成 REFCOUNTED**；
2. 工作线程不持有父对象引用计数；
3. 队列/后端/工作区保持结构性 OWNED；
4. Global 的生命周期固定保护（pin）可在 #104 重做，但不能用裸指针 + 引用计数 CAS 简化；
5. 进程存活对象计数永远不等价于对象引用计数；
6. 构造回滚已采用“先证明安全，再释放内存”；
7. 引用计数原语只有真实对象选择 REFCOUNTED 后才进入生产环境；禁止为了完成检查清单引入未使用基础设施。

尚未冻结：

- 2.0 公开 Logger API 是否提供长生命周期 get/put；
- Global 外观接口未来是否被新对象模型替换（当前保留）；
- 最终冻结时是否调整现有 Logger 关闭/销毁/公开状态 API；
- 哪个未来对象第一个真正需要 REFCOUNTED。

这些未来冻结问题进入 #104/#108 决策；在新决策落地前，当前公开 API 与以上生命周期防护持续适用。
