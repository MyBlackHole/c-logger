# 错误处理

错误处理是资源与持久性契约的一部分。清理过程不得意外覆盖真正解释操作失败原因的错误。

## 内部与公开返回值约定

内部辅助函数通常采用：

```text
0        成功
负 errno 错误码
```

已迁移的公开状态 API 同样使用 `0/-errno`，所有正常返回保留调用方 `errno`。
这包括进程初始化、实例所有权、默认绑定、刷新/重开、记录、状态/指标查询和
Console。直接检查返回值，不从保留的 `errno` 推测调用结果：

```text
0        成功
负 errno 错误码       失败，调用方 errno 保持原值
```

级别设置、TLS上下文和脱敏辅助函数尚未统一；内部调用 libc/POSIX 的适配层
仍可接收 `-1+errno`，但必须在明确边界转换并保留主错。不能全局更改内部
作用域的 errno 处理来静默改变尚未迁移入口。

记录失败可能发生于入队或输出之后，不能据此安全重试；查询则只有最终收尾
成功才发布输出，任何失败保持原槽。详细见[记录合同](v2/RECORD_API.md)和
[查询合同](v2/QUERY_API.md)。

## 保留第一个有意义的错误

当主体操作失败，同时清理也失败时，需要明确哪个错误在语义上具有更高优先级。

对于普通回滚清理，应保留主体操作错误：

```text
操作错误
    |
尽力清理
    |
返回原始错误
```

因此自动释放内存/关闭辅助接口会保存进入清理前的 `errno`。

默认生命周期锁释放证明失败属于安全例外：它优先返回解锁错误并保守保留借用，
不能以“保留主错”为由假装资源已经归还，见[控制合同](v2/CONTROL_API.md)。

## 能产生错误的最终处置必须保持显式

某些释放操作并不只是“普通清理”。它们的失败本身就是 API/持久性结果的一部分，例如：

- `fsync()`；
- 命名空间变化后的目录同步；
- 轮转/重新打开状态切换；
- 明确要求可观察 close 错误时的最终关闭；

不要把这些操作隐藏在会丢弃结果的析构路径中。

## 已锁存的后端错误

Logger 实例会记录第一次后端 I/O 错误。后续成功不能抹掉此前输出已经失败的证据。

指标会区分：

- 已尝试/已完成记录；
- 成功输出记录；
- 失败记录；
- 第一个已锁存错误。

因此，一次刷新即使完成了当前工作，仍可能继续报告更早发生的已锁存错误。

## 部分写入

后端短写/部分写入不会被静默提升为成功。如果部分批处理无法重建逐记录确认状态，
实现会保守地把受影响批次归类为“未确认”。

## 验证错误

应尽可能在获取高成本资源或产生外部可见副作用之前拒绝非法配置。

不得静默掩盖：

- 未知输出位；
- 非法枚举；
- 非法文件模式；
- 不可能满足的队列容量；
- 不受支持的平台/后端语义。

## 清理与 errno

临时 fd/FILE 所有权的自动清理会保存并恢复 `errno`。
析构路径不得意外把：

```text
ENOMEM
```

变成：

```text
回滚 close 产生的 EBADF
```

除非关闭本身就是当前需要报告的操作。

## 错误路径测试

构造函数/错误路径测试应覆盖每个有意义的资源获取边界之后的失败，并验证：

- 无资源泄漏；
- 无重复释放；
- 无陈旧所有者；
- 无遗留锁；
- 对象/线程数量正确；
- 返回错误/`errno` 正确；
- 在受支持场景中，下一代次/重试行为正确。
