# 代码与注释规范

## 语言原则

c-logger 的源码注释、内部设计说明和工程文档使用简体中文。完整范围与兼容边界见
[项目语言约定](PROJECT_LANGUAGE.md)。

以下固定名称保留原样，以避免翻译造成技术歧义：

- C/POSIX/Linux API 和函数名，例如 `pthread_join`、`fdopen`；
- 代码标识符，例如 `emit_mu`、`g_lifetime_lock`；
- 标准内存序，例如 `memory_order_acquire`；
- 所有权/生命周期约定标记，例如 `OWNED`、`BORROWED`、`MOVED`、
  `SHARED`、`REFCOUNTED`；
- 标准错误码，例如 `EINVAL`、`EPIPE`；
- Linux/POSIX 固定术语、协议名称和外部引用原题。

概念解释使用中文，不能因为标识符是英文就把整个说明写成英文。例如：

```c
/* 通过 memory_order_release 发布负载。 */
```

保留 `memory_order_release`，不另造译名替换它。

## 注释应该解释什么

优先解释代码无法直接表达的约束：

1. **所有权**：谁拥有资源、何时转移、最终谁释放；
2. **生命周期**：对象何时开始可见、何时允许销毁；
3. **锁机制**：哪把锁保护什么，固定锁顺序是什么；
4. **并发**：发布/消费、原子内存序、线程等待/生命周期固定/引用计数关系；
5. **错误语义**：哪些错误必须向上返回，哪些清理错误可以忽略；
6. **持久性**：fsync/rename/目录 fsync 的顺序为什么不能变化；
7. **平台约束**：Linux/ELF、GNU C 扩展、fork/线程取消等边界。

不要写只重复代码表面的注释，例如：

```c
i++; /* i 加 1 */
```

## 所有权注释格式

复杂资源建议在创建、转移和最终释放位置分别写清楚：

```c
/*
 * 所有权转移：词法作用域内的临时所有者 -> struct logger_queue。
 * 最终由 logger_queue_destroy() 释放。
 */
q->slots = no_free_ptr(slots);
```

普通多行块注释的首尾符号各自独占一行，中间每行以对齐的 `*` 开头；
单行字段说明可保留 `/* 说明 */`。注释说明所有权、上下文、失败责任和同步理由，
不复述显然的签名或逐步翻译代码。公开/私有接口均须区分状态码、计数和谓词；
既有成组合同可复用，不为每个简单访问器增加重复模板。

长期持有字段应在结构体声明附近注明：

```c
/* 创建成功后由 logger_t 拥有；等待工作线程退出后才能释放。 */
struct logger_worker_workspace *worker_workspace;
```

## 锁和并发注释

不能只写“线程安全”。必须说明保护关系或协议，例如：

```c
/* q.wait_mu 只负责休眠/唤醒，不负责发布槽位负载。 */
```

涉及原子操作时，说明它承担的是预留、发布、完成确认还是生命周期管理；
禁止用“原子所以线程安全”这种模糊表述。

使用 `guard()/ACQUIRE()` 前必须先确认锁层级。单锁、词法作用域内、解锁错误无业务语义
的路径优先使用守卫；多锁、需要感知取消、跨作用域所有权或需承载错误的解锁保持显式。
完整规则见 [锁规范](LOCKING.md)与[锁矩阵](LOCK_MATRIX.md)。

## 错误与清理注释

如果析构/关闭的错误被故意忽略，要解释原因。

如果 `close`、`fsync`、`closedir`、rename 或持久化失败会改变 API 结果，
必须说明为什么保持显式收尾，不能隐藏到自动清理。

## 历史英文注释迁移

不要求为了翻译而一次性重写整个历史文件。

但从本规范生效后：

- 新增解释性注释必须使用中文；
- 修改到某段已有代码时，该段相关英文解释性注释应同步中文化；
- API 名、变量名、固定标准术语继续保留原样；
- 历史文档可分批补充中文导读，原始证据保持可核验，不能因翻译改变行为、ABI 或协议语义。

## 对外文档

面向当前项目开发者的内部文档使用中文。

如果未来需要英文发布文档，应单独维护英文版本或生成版本，不要把中英文逐句混写到
核心源码注释中。
