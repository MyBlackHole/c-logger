# Linux 编码规范符合性收敛计划

本计划响应维护者“满足 linux 内核代码开发规范为止”的持续目标。
它规定完整范围、规范依据和验收方法；**不是完成声明，也不是第二份任务总账**。
唯一工作位、每项任务的状态、PR 和完成回执始终在
[#100](https://github.com/MyBlackHole/c-logger/issues/100)，工程归属为
[#106](https://github.com/MyBlackHole/c-logger/issues/106)。任务逐项合并、核对主线并回写后，才开始下一项。

## 全部范围与适用边界

范围由 Git 跟踪文件枚举，不手写一个仅覆盖容易通过文件的允许列表：

```sh
git ls-files '*.[ch]' '*.cc' '*.cpp' '*.hpp' '*.cxx' '*.hh'
```

起始源码共有 **165 个自有 C/C++ 文件**：`src/` 36、`include/` 3、`tests/` 113、
`examples/` 11、`tools/` 2。新文件自动进入最终检查范围。
生产代码、测试驱动、示例、下游 C/C++ 消费样例和诊断程序均在范围内。
生成头文件须审查其生成入口；Python/shell 中内嵌的 C 正负例须按用途审查，
不能为美化示例而删除测试故意制造的错误。

这是现有 Linux 用户态 C 库的编码收敛，不是移植成内核模块：

- 适用的 C 排版、命名、类型表达、原型、注释、宏、函数组织和错误处理要求逐项落实。
- `pthread`、libc、C11 内存模型及用户态分配接口按实际执行环境核对，
  不替换成 `spinlock`、GFP、`printk` 或内核私有 UAPI。
- 公开 API/ABI、格式、状态码和测试协议保持兼容。不透明对象与有真实类型隔离作用的类型
  可使用官方允许的 typedef；普通可直接访问的内部结构体不能仅因已有名字就视为例外。
  公开的可访问类型别名必须逐个记录兼容需求和处理方案，不能把“公开”作为全类别豁免。
- 单一宿主所有者、受保护的借用和 worker join 必须有完整存活证明；
  多个独立生命周期所有者才需要对应共享所有权机制。不能把持锁当作存活证明，
  也不能仅为形式接近而插入无实际所有权作用的引用计数。
- Kconfig、内核导出和设备日志等专属条款须依据实际不存在的对象标明不适用。
  一节同时包含可迁移原则时，不能把整节一并排除。
- 法律原文和已有第三方接口不作语言或许可改写。checkpatch 的许可标签提示须另核对归属，
  不从编码要求推导新的许可授权。

任何保留差异都必须列明文件/符号、条款、成立条件与验证证据；
没有依据的差异仍是待处理项，不能由“用户态适配”笼统放行。

`baseline-scan.json`、`baseline-summary.json`、`checkpatch/`。
这些文件是检查产物，不构成新的生产源码或权威状态账本。
精确的起始 Git 提交、上游提交和检查命令允许重建报告，不能用当前摘要覆盖原件。

## 串行实施顺序

下列步骤是同一目标的实施顺序，不是同时在制的任务。每项开始前，
把准确问题、文件范围、完成条件和依赖登记到 #106/#100；同一时刻只执行一项。
本计划不预先把尚未实现的检查或人工例外当作已批准。

### KS-001：固定规范与全量差异基线（当前项）

交付本计划及项目规范入口，保存真实扫描原件；独立审查来源、范围、统计和逐节覆盖。
只改文档，无业务行为或接口变化。完成文档 PR、主线 CI 和两处回执后才进入 KS-002。

### KS-002：完整范围的纯排版收敛

1. 重新枚举 165 文件及任何新增 C/C++ 文件，使用固定格式器处理实际差异文件。
2. 检查 `src/`、`tests/` 中的 37 个起始差异文件；不是只修生产目录。
3. 用 C token 对照确认非空白 token、字符串/字符字面量、预处理续行没有行为变化；
   保留每文件前后检查和完整原始差异。不得仅依靠 `git diff -w` 证明宏语义不变。
4. 运行全文件格式检查、现有增量门禁、相关格式正反例；Xmake 及真实 CI 验证改后代码。
5. 独立审查、正常合并、主线树与 CI、回执完整闭环。该项不顺带改名字、类型或逻辑。

### KS-003：类型表达与声明

1. 列出 `src/` 私有结构体/枚举/冗余别名和全部使用者；普通结构体改具名 struct。
2. 同步必要的测试驱动、包装器声明、文档及既有 Clang AST 规则识别身份，
   保持原有禁止拥有者复制/借用重包的能力，不增加范围外 AST 规则。
3. 原型补参数名，声明/定义属性一致；对裸 `unsigned` 等类型拼写作不改变类型的规范化。
4. 公开兼容别名、不透明对象、宏生成类型逐个记录处理依据；禁止整体豁免或偷偷破坏消费 API。
5. AST 检查器若需适配，先用既有正反例证明旧禁止能力在新拼写下仍被拒绝，再改识别；
   运行共享/静态、C/C++、布局/导出符号及精确头文件消费验证。

### KS-004：注释与接口说明

统一长块注释格式，保留中文解释、法律原文、历史证据和机器兼容标识。
复核头文件参数、返回、所有权与上下文说明；删除复述代码的冗余说明，而不是删除必要的同步证明。
用 token/字符串对照及接口文档检查证明不混入行为改动。

### KS-005：宏、布尔语义、返回约定与条件编译

逐条处理辅助报告的真实问题；特别审查 cleanup 生成器、测试断言宏、重复求值、
隐式返回/捕获、常量表达式与 GNU 扩展。保留有真实必要性的语法抽象，并以编译正反例证明。
按布局和协议选择 bool，不把位图、错误码或原子协议改成普通布尔。
返回约定与平台启闭处理须保持公开合同；行为变化需要先复现并登记独立修复，不混在纯风格提交里。

### KS-006：函数与对象协议人工审查

枚举全部函数，按职责、嵌套和局部状态复核生产/测试/示例；
优先处理 create_logger 等多阶段构造和复杂文件路径，测试长驱动也不能直接跳过。
拆分围绕真实阶段或职责，不能仅为满足行数制造包装。
逐对象核对矩阵第 7、11、14、16、22 节的取得、发布、借用、停止和释放证明；
复用准确现有证据，必要变更运行有针对性的失败/取消/并发回归。
较长但简单的函数须保留具体理由，不能把所有长函数笼统列为例外。

### KS-007：完整范围的持续门禁

复用 `scripts/check_source_format.py` 和现有工作流补全全仓检查入口，
覆盖历史文件、新文件、合法语法、工具/版本失败和带空格路径；保留增量检查的明确语义。
checkpatch 输出按具体来源、符号和规则适用性分类；不建立吞掉所有诊断的宽泛忽略列表。
仅对人工无法替代的真实规则补门禁，不为了增加检查数量新造泛化 AST 框架。

### KS-008：整体完成审计

对最终 main 的完整当前文件集重新运行格式/规则/编译与适用回归，
逐节回读矩阵并把证据绑定到准确 commit/tree、实际命令、CI 作业与结果。
旧基线清单不能代替最终新文件清单；修复了多少行、工作流全绿、一个 checker 无输出都不是整体证明。
每条未解决、未验证或无依据的保留差异仍算未完成。
全部适用要求都有强证据、任务回执和主线闭环后，才能把持续目标标为完成。

## 验证与输出约束

项目构建、测试、打包仍以 Xmake 为权威，先从 VERSION 设置 LOGGER_PROJECT_VERSION。
TMPDIR/TMP/TEMP/XMAKE_TMPDIR、编译缓存、日志和检查产物均指向工作区；
已知硬编码 `/tmp` 的测试不得直接运行，先在对应单项中处理可重定向问题。
不能为追求完整验证而先违反输出目录约束。

每项记录实际通过、失败、跳过和未运行；准确头、合成受测提交、源码树与合并后主线分开。
共享配置里的静态支持库注入不能冒称生产共享 DSO 注入，TSan 的 31 项检测器跳过继续明确列出。
本目标不自动消除既有宿主/检测器风险，也不修改正式签收、版本、标签和 Release。
